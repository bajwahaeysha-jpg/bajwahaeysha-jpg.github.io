The brief

ATM Simulation is a C++ console application built to practice the fundamentals behind real ATM software: a persistent balance, a menu the user can return to after every action, and input that has to be validated instead of trusted. Built in Dev-C++, with no GUI to lean on — every interaction happens through the terminal, so the program's logic has to carry the whole experience.

What it does

  • Deposit — adds a user-entered amount to the current balance
  • Withdraw — subtracts an amount after checking there's sufficient balance, rejecting the request otherwise
  • Check Balance — prints the current balance without changing it
  • Exit — ends the session cleanly

After every operation, the program loops back to the main menu rather than exiting, so a user can deposit, withdraw, and check their balance in the same session — closer to how a real ATM session behaves than a single run-once script.

How it's built

The whole simulation runs in a single C++ file, structured around a loop that displays the menu, reads the user's choice, and dispatches to the matching operation. The balance is tracked in memory for the session, and withdrawals are checked against it before being applied, so the balance can never go negative through normal use. Input is read and validated at each prompt rather than assumed to be well-formed, since a console app has no form fields to constrain what the user types.

A session, not a script

The menu loop lets a user perform several operations in one run, instead of the program exiting after a single action.

Balance integrity

Withdrawals are checked against the current balance before they're applied, so the account can't go negative through normal use.

No GUI to hide behind

With only the console for input and output, the program logic itself has to carry the whole user experience.

Reflections

Working without a GUI forced me to think harder about program flow and edge cases — what happens on an invalid choice, an overdraft attempt, or a non-numeric input — since there's no form validation to catch mistakes for you. If I extended this, I'd add file-based persistence so the balance survives between runs, and PIN-based login for multiple accounts.
